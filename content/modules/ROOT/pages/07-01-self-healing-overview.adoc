== The Problem We Identified

In xref:06-01-potential-imp-ref.adoc[Section 6.1] we asked ourselves some hard questions about the prototype:

[quote]
____
Is our current application robust enough? Describe what scenarios might make it harder to use?
____

[quote]
____
If too many users connect at the same time, it might overwhelm either the app, the database, the LLM...
____

[quote]
____
Which parts seem to still be manual and time-consuming, and how could we automate them better, to avoid human errors if we can?
____

These are not hypothetical concerns. In production, the {company-name} claims processing application **will** experience:

* *Memory pressure* -- claim images and LLM responses consume memory; a burst of concurrent users can push containers toward their limits
* *CPU spikes* -- image recognition and LLM inference are CPU-intensive; peak hours cause throttling
* *Crash loops* -- a bad deployment or dependency failure can put pods into CrashLoopBackOff
* *Database outages* -- network hiccups or disk pressure can cut the app off from PostgreSQL
* *Cascading failures* -- one failing component degrades the entire claims workflow

Today, a human operator would need to notice the problem, diagnose it, and fix it -- often at 2 AM. That is exactly the kind of *manual, time-consuming, error-prone* process Section 6 warned us about.

== The Answer: Hybrid Operations

This section shows two workflows that sit next to each other.

The repairs you will watch in section 7.4 are rule-based. Prometheus alert rules notice memory pressure, CPU throttling, crash loops, a missing database allow, and disk pressure. `parasol-remediator` in the `parasol-insurance` namespace reads those firing alerts and runs a fixed action for each name: delete the `ic-app` pod, roll the deployment back, restore database egress, or delete the fill file.

The Isolation Forest is a separate machine-learning workflow. You train it on {company-name} container metrics, save `model.pkl`, and then use one decision exercise where that model's verdict chooses whether to repair. The coordination engine in `self-healing-platform` does not subscribe to these five Parasol alerts, and `parasol-remediator` does not send metrics to the model.

== Architecture

The self-healing platform runs in its **own namespace** (`self-healing-platform`). The {company-name} application, its alerts, and `parasol-remediator` stay in `parasol-insurance`.

[source,text]
----
parasol-insurance namespace                 self-healing-platform namespace
┌──────────────────────────────────┐       ┌────────────────────────────────┐
│ ic-app (Flask + React)           │       │ anomaly-detector               │
│ claimdb (PostgreSQL)             │       │   (KServe InferenceService)    │
│ ServiceMonitor ──scrape──► Prometheus    │                                │
│ PrometheusRule                   │       │ coordination-engine (Go)       │
│ parasol-remediator ──repairs──► pods     │   does not consume these alerts│
└──────────────────────────────────┘       └────────────────────────────────┘
----

The key integration points for the rule-based repairs are:

* **ServiceMonitor** -- Prometheus scrapes the {company-name} app's `/metrics` endpoint every 15 seconds
* **PrometheusRule** -- Alert rules fire when memory exceeds 85%, pods crash-loop, CPU is throttled, the database allow policy is removed, or the database volume fills
* **parasol-remediator** -- Watches those five alerts and runs the matching repair
* **NetworkPolicy** -- Allows `ic-app` to reach DNS, MinIO, Milvus, the in-namespace model server, PostgreSQL, and the platform namespace. The PostgreSQL allow is its own policy so a fault can remove it
* **RBAC** -- Lets the coordination engine read pods in `parasol-insurance`. That binding is present. These five repairs do not go through that engine

In this section you will:

1. **Deploy** the KubeHeal integration overlay onto your existing {company-name} application
2. **Explore** the monitoring and alerting that was just created
3. **Inject real faults** and watch `parasol-remediator` repair them from alert rules
