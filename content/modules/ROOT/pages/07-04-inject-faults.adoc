= Inject Faults and Watch Self-Healing
include::_attributes.adoc[]

[quote]
____
In xref:06-01-potential-imp-ref.adoc[Section 6.1]: _"Is our current application robust enough? Describe what scenarios might make it harder to use?"_
____

Let's find out. We are going to deliberately break the {company-name} application using chaos engineering scripts, and then watch `parasol-remediator` repair each problem.

== Preparation

Open **two terminals** side by side:

* **Terminal 1** -- Watch pods in real time:
+
[source,terminal]
----
oc get pods -n parasol-insurance -w
----

* **Terminal 2** -- Run the chaos scripts (from the parasol-insurance repository root)

== Scenario 1: Memory Leak (OOMKill)

This simulates what happens when a burst of concurrent claims processing pushes the application's memory toward its limit.

In Terminal 2, run:

[source,terminal]
----
./chaos/memory-leak.sh
----

*What happens:*

. The script holds anonymous memory until the container is using about 90% of its limit.
. `ParasolOOMRisk` fires after usage stays above 85% for 30 seconds.
. `parasol-remediator` deletes the `ic-app` pod.
. The Deployment starts a replacement. In Terminal 1 you should see the pod go from `Running` to `Terminating`, then a new pod become `Running`.

== Scenario 2: CPU Spike

In Terminal 2, run:

[source,terminal]
----
./chaos/cpu-spike.sh
----

This runs a 120 second busy-loop. The container CPU limit is 2, so the extra workers are throttled. `ParasolCPUThrottling` fires when more than 25% of CPU periods are throttled, and `parasol-remediator` deletes the pod.

== Scenario 3: Crash Loop

In Terminal 2, run:

[source,terminal]
----
./chaos/crash-loop.sh
----

This patches the deployment with an invalid command. The new pod exits immediately. After more than 3 restarts in 10 minutes, `ParasolCrashLooping` fires and `parasol-remediator` rolls the deployment back to the previous revision.

To roll back yourself if the pod is still crash-looping:

[source,terminal]
----
./chaos/crash-loop.sh --rollback
----

== Scenario 4: Network Partition (Database Unreachable)

In Terminal 2, apply the chaos NetworkPolicy:

[source,terminal]
----
oc apply -f chaos/network-partition.yaml
----

This creates NetworkPolicy `chaos-block-db-access`, which blocks `ic-app` egress except DNS and the platform inference port. `ParasolDBConnectionFailure` fires while that policy exists, and `parasol-remediator` deletes it.

== Scenario 5: Disk Pressure

In Terminal 2, run:

[source,terminal]
----
./chaos/disk-pressure.sh
----

This writes a file on the PostgreSQL volume until usage is just over 70% and stops before 90%. `ParasolDiskPressure` fires, and `parasol-remediator` deletes `/var/lib/pgsql/data/chaos-fill`.

To remove the file yourself:

[source,terminal]
----
./chaos/disk-pressure.sh --cleanup
----

== Summary

[cols="2,2,2"]
|===
| Script | Alert | Repair

| `memory-leak.sh`
| `ParasolOOMRisk`
| Delete the `ic-app` pod

| `cpu-spike.sh`
| `ParasolCPUThrottling`
| Delete the `ic-app` pod

| `crash-loop.sh`
| `ParasolCrashLooping`
| Roll the deployment back

| `network-partition.yaml`
| `ParasolDBConnectionFailure`
| Delete `chaos-block-db-access`

| `disk-pressure.sh`
| `ParasolDiskPressure`
| Delete the fill file
|===

`parasol-remediator` performs the repair column. The coordination engine does not subscribe to these alerts.
