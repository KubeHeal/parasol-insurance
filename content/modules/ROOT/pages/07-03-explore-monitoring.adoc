Now that the integration overlay is deployed, Prometheus is already scraping the {company-name} application's metrics. Let's see what it's collecting.

== Step 1: Check Monitoring Resources

[source,terminal]
----
oc get servicemonitor,prometheusrule -n parasol-insurance
----

[source,terminal]
----
NAME                                                     AGE
servicemonitor.monitoring.coreos.com/parasol-insurance   6h1m
servicemonitor.monitoring.coreos.com/qwen-metrics        127m

NAME                                                            AGE
prometheusrule.monitoring.coreos.com/parasol-insurance-alerts   6h1m
----

`AGE` will not match. Both ServiceMonitors and the `parasol-insurance-alerts` rule should be present.

== Step 2: View Metrics in the {ocp} Console

. Open the {ocp} Console
. Navigate to **Observe** > **Metrics**
. In the query box, enter:
+
[source,promql]
----
container_memory_working_set_bytes{namespace="parasol-insurance", container!=""}
----
+
. Click **Run Queries**

The graph has one line per container. Ignore lines whose container is `POD` (they sit near zero). On an idle lab cluster the working set looked like this:

[cols="2,2,1"]
|===
| Pod | Container | Working set

| `claimdb-...`
| `postgresql`
| about 40 MiB

| `ic-app-...`
| `insurance-claim-app`
| about 900 MiB

| `milvus-...`
| `milvus`
| about 160 MiB

| `minio-...`
| `minio`
| about 110 MiB

| `parasol-remediator-...`
| `remediator`
| about 5 MiB

| `qwen-predictor-...`
| `kserve-container`
| about 3.9 GiB
|===

The claims container is `insurance-claim-app`, about 900 MiB while idle on this stack. `kserve-container` is large because the Qwen model is loaded. Exact numbers move with load.

Try another query to see CPU usage:

[source,promql]
----
rate(container_cpu_usage_seconds_total{namespace="parasol-insurance", container!=""}[5m])
----

At idle, `insurance-claim-app` is a small fraction of one core (about 0.002). The other containers are in the same range, except short bursts from `milvus`.

The same series is available from the CLI. Thanos answers with JSON when the request carries a token. An HTML login page or `401` means the query missed the token.

[source,terminal]
----
PROM=$(oc get route thanos-querier -n openshift-monitoring -o jsonpath='{.spec.host}')
curl -sk -H "Authorization: Bearer $(oc whoami -t)" \
  --data-urlencode 'query=container_memory_working_set_bytes{namespace="parasol-insurance",container="insurance-claim-app"}' \
  "https://${PROM}/api/v1/query"
----

[source,terminal]
----
{"status":"success","data":{"resultType":"vector","result":[{"metric":{"container":"insurance-claim-app","namespace":"parasol-insurance"},"value":[1792613793.431,"954970112"]}]}}
----

`"status":"success"` and a numeric sample in `value` are the check. The live body includes more metric labels. The timestamp and byte count will differ.

== Step 3: Check Alert Rules

. In the {ocp} Console, navigate to **Observe** > **Alerting** > **Alerting rules**
. Search for `Parasol`

You should see seven rules. The same list from the CLI:

[source,terminal]
----
oc get prometheusrule parasol-insurance-alerts -n parasol-insurance -o jsonpath='{range .spec.groups[0].rules[*]}{.alert}{"\t"}{.labels.severity}{"\n"}{end}'
----

[source,terminal]
----
ParasolHighErrorRate	warning
ParasolHighLatency	warning
ParasolOOMRisk	critical
ParasolCrashLooping	critical
ParasolDBConnectionFailure	critical
ParasolCPUThrottling	warning
ParasolDiskPressure	critical
----

[cols="2,1,3"]
|===
| Alert | Severity | Condition

| `ParasolHighErrorRate`
| Warning
| HTTP 5xx rate above 5% for 2 minutes

| `ParasolHighLatency`
| Warning
| p95 latency above 2 seconds for 5 minutes

| `ParasolOOMRisk`
| Critical
| `insurance-claim-app` memory above 85% of its limit for 30 seconds

| `ParasolCrashLooping`
| Critical
| A pod restarted more than 3 times in 10 minutes

| `ParasolCPUThrottling`
| Warning
| More than 25% of CPU periods throttled

| `ParasolDBConnectionFailure`
| Critical
| NetworkPolicy `chaos-block-db-access` is present for 30 seconds

| `ParasolDiskPressure`
| Critical
| `claimdb` volume usage above 70% for 30 seconds
|===

With no fault injected, every rule is **Inactive** (green) in the console. `parasol-remediator` repairs the five fault alerts (`ParasolOOMRisk`, `ParasolCPUThrottling`, `ParasolCrashLooping`, `ParasolDBConnectionFailure`, `ParasolDiskPressure`). It does not act on `ParasolHighErrorRate` or `ParasolHighLatency`. The next section fires the five fault alerts.
